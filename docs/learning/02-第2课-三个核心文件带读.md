## 0. 全景：一次请求的完整调用链

```
main.py (asyncio.run)
  └─ Manus.create()                          # app/agent/manus.py:76 工厂方法
       └─ initialize_mcp_servers()           # 接浏览器(browser-use)等MCP工具
  └─ agent.run("你的任务")
       └─ BaseAgent.run()                    # app/agent/base.py:116 —— 总循环
            └─ while 未到max_steps 且 未FINISHED:
                 └─ self.step()
                      └─ ReActAgent.step()   # app/agent/react.py:33 —— 一步 = think + act
                           ├─ ToolCallAgent.think()   # app/agent/toolcall.py:39  问模型
                           └─ ToolCallAgent.act()     # app/agent/toolcall.py:131 干活
```

**一句话总结：`run` 是发动机（管步数和状态），`step` 是活塞（思考+行动），`think` 是化油器（问模型调哪个工具），`act` 是车轮（真正执行）。**

## 1. schema.py —— 全项目的"名词表"（先读它，后面全是它的词汇）

**路径**：`app/schema.py`（188 行）

| 结构 | 行号 | 作用 | 面试要点 |
|---|---|---|---|
| `Role` 枚举 | 7-16 | 消息只有 4 种角色：system/user/assistant/**tool** | tool 是独立角色——这是 Function Calling 和普通聊天的结构区别 |
| `ToolChoice` | 20-29 | none/auto/required 三种模式 | auto=模型自己决定调不调工具；required=必须调；none=禁止 |

| `Function` | 41-43 | `{name, arguments}`——注意 **arguments 是字符串不是字典** | 为什么是字符串？模型输出本质是文本，JSON 由框架侧解析——解析失败要兜底（见 toolcall.py:207） |

## 2. agent/base.py —— 发动机：run() 主循环（116-154 行）

```python
while (self.current_step < self.max_steps and self.state != AgentState.FINISHED):
    self.current_step += 1
    step_result = await self.step()          # ← 子类实现的一步
    if self.is_stuck():                      # ← 卡死检测！
        self.handle_stuck_state()
```

**四个必背细节：**

1. **max_steps 默认 10**（第 40 行），但 ToolCallAgent 改成 30（toolcall.py:36）、Manus 是 20（manus.py:51）——**每个 Agent 子类可以覆盖步数上限**。
2. **两种停止**：模型主动停（state=FINISHED）或步数耗尽强制停（149-152 行，追加 `"Terminated: Reached max steps"`）。
3. **is_stuck() 卡死检测（170-186 行）**：数最近消息里**内容完全相同的 assistant 消息**出现次数，≥2 次（duplicate_threshold，第 43 行）判定卡死。**handle_stuck_state（163-168）不重启、不报错，而是往 next_step_prompt 前面塞一句"你重复了，换策略"**——用提示词纠偏，成本几乎为零。这是"LLM 会陷入循环"这个真实工程问题的廉价解法，**面试讲这个是亮点**（说明你踩过或读懂过真实的坑）。
4. **run() 结束必做 `SANDBOX_CLIENT.cleanup()`**（153 行）——资源清理意识。

**面试官会怎么问**：
- "你的 Agent 怎么防止死循环？"→ 双保险：max_steps 硬上限 + is_stuck 重复检测软纠偏。
- "卡死检测为什么比对内容而不是比对工具调用？"→ 相同内容意味着模型在原地踏步；比对内容实现最简单且足以覆盖大多数循环。

## 3. agent/react.py —— 一步 = think + act（全文只有 38 行！）

```python
async def step(self) -> str:
    should_act = await self.think()      # 问模型：下一步干啥
    if not should_act:
        return "Thinking complete - no action needed"
    return await self.act()              # 执行
```

- `think()` 和 `act()` 是**抽象方法**（26-31 行）——ReActAgent 只规定"每一步必须先想后做"，具体怎么想怎么做留给子类。
- **这就是为什么 OpenManus 易于二开**：你写新 Agent 时只需要实现 think/act，循环、卡死检测、记忆管理全部继承。
- 返回 `False` 的含义：模型认为不需要调工具了（纯回答），循环会因返回空结果而自然收敛或由 Terminate 结束。

**面试官会怎么问**："ReAct 的 Thought→Action→Observation 在代码里分别对应什么？" → Thought=think() 里模型的输出内容；Action=think() 解析出的 tool_calls；Observation=act() 执行后写回 memory 的 tool_message。**三者全部落在消息列表里，这就是为什么 Memory 是核心数据结构。**

## 4. agent/toolcall.py —— 心脏：think() 和 act()（W1 精读的重中之重）

### think()（39-129 行）：问模型要"下一步"

1. 先把 `next_step_prompt`（"你现在处于什么状态、该干嘛"的提醒）作为 user 消息追加（41-43 行）。
2. 调 `llm.ask_tool()`，关键参数：`tools=self.available_tools.to_params()`（54 行）——**把所有工具的 schema 打包发给模型**，模型才知道有什么工具可调。
3. **Token 超限兜底（60-73 行）**：捕获 TokenLimitExceeded → 写一条 assistant 消息说明原因 → **state=FINISHED 优雅收场**，而不是崩溃。第三种停止条件！
4. 解析 `response.tool_calls`（75-77 行）；把模型的回复（含 tool_calls）追加进 memory（106-112 行）。
5. 返回值决定 act 执行与否：AUTO 模式下没工具调用但有文本 → 返回 `bool(content)`（118-119 行）；有工具调用 → True（121 行）。

### act()（131-172 行）：真正执行

1. 遍历每个 tool_call → `execute_tool()`（146 行）。
2. `max_observe` 截断（148-149 行）——Manus 设 10000 字符（manus.py:50），**防止一个工具输出巨量文本撑爆上下文**。
3. 结果包成 `Message.tool_message(content, tool_call_id, name)` 写回 memory（156-161 行）——**tool_call_id 在这里和请求配对**，这就是 schema.py 里那个 id 的用途。
4. 工具若返回图片，追加独立的 user 消息（162-168 行）。

### execute_tool()（174-216 行）：错误处理的教科书

```python
args = json.loads(command.function.arguments or "{}")   # 185行：字符串→字典，可能炸
result = await self.available_tools.execute(name=name, tool_input=args)  # 189行：真正执行
```

**三类错误全部"变成 Observa­tion 喂回模型"而不是抛异常崩掉循环：**
- 工具不存在（180-181）→ `"Error: Unknown tool"`；
- JSON 解析失败（207-212）→ `"Error parsing arguments"`；
- 执行任意异常（213-216）→ `"Error: Tool xxx encountered a problem"`。

**面试金句（背下来）**：「工具执行失败不会终止 Agent——错误信息会作为 Observation 回给模型，模型看到错误后会自己调整参数重试或换工具。这是 Agent 自愈能力的基础，代价是可能反复失败耗尽步数，所以需要 max_steps 兜底。」——这一句话覆盖考核题 1/2 和"工具调用失败怎么办"。

### Terminate 工具 = 第四种停止条件

`special_tool_names=[Terminate().name]`（31 行）；`_handle_special_tool`（218-227 行）：模型调 `terminate` 工具 → `state = AgentState.FINISHED` → run() 循环退出。**模型用"调一个工具"的方式表达"我做完了"**——把控制流也统一成工具调用，这个设计很优雅。

## 5. tool/base.py —— 你的 W2 工具将从这里继承（78-173 行）

```python
class BaseTool(ABC, BaseModel):
    name: str          # 工具名，模型看到的就是它
    description: str   # 给模型看的说明书——写得越清楚模型调用越准
    parameters: Optional[dict]  # JSON Schema：参数名/类型/必填/枚举

    @abstractmethod
    async def execute(self, **kwargs) -> Any   # 真正干活的地方——你要写的核心

    def to_param(self) -> Dict:                # 124-137行：转成 OpenAI function calling 格式
        return {"type": "function", "function": {
            "name": ..., "description": ..., "parameters": ...}}
```

- `ToolResult`（38-75 行）：`output / error / base64_image / system` 四字段；`success_response()` / `fail_response()`（147-173）是规范出口——**成功失败都返回 ToolResult，而不是 raise**（呼应 execute_tool 的兜错哲学）。
- **W2 你写工具 = 定义 name/description/parameters + 实现 execute()**，注册则是塞进 `ToolCollection`（见第 7 节）。
- `description` 和 `parameters` 是写给**模型**看的文档，不是写给人的——模糊的描述会直接导致模型传错参数。这解释了"为什么 prompt 工程和工具设计是一回事"。

**面试官会怎么问**："模型怎么知道有哪些工具、各有什么参数？" → 每轮 think() 时 `to_params()` 把全部工具的 JSON Schema 随请求下发；模型按 schema 生成 arguments。

## 6. flow/planning.py —— 任务分解：先拆计划，再逐步执行（94-134 行主流程）

```
execute(input)
  ├─ _create_initial_plan()        # 136-211行：让 LLM 调 planning 工具生成计划（步骤列表+状态）
  ├─ while True:                   # 112行
  │    ├─ _get_current_step_info() # 213行：找第一个未完成步骤；正则提取 [AGENT名] 路由标记（245行）
  │    ├─ get_executor(step_type)  # 77行：按标记选执行 Agent，没有就 fallback 主 Agent
  │    ├─ _execute_step()          # 277行：把"计划全文+当前步骤"拼成 prompt → agent.run()
  │    └─ _mark_step_completed()   # 306行
  └─ _finalize_plan()              # 406行：LLM 总结整个计划
```

- **计划不是代码，是数据**：plan 存在 `planning_tool.plans[plan_id]` 字典里（steps/step_statuses/step_notes），状态用 `[✓][→][!][ ]` 标记（37-42 行）。
- **每个步骤内部又是一个完整 ReAct 循环**（_execute_step 调 agent.run）——所以这是"循环套循环"：外层 Plan-and-Execute，内层 ReAct。**这就是"规划 Agent"和"执行 Agent"分层的最小样本**。
- 官方 README 明确标注这个 multi-agent 版本为 **unstable**（README.md:166）——我们第 3 周不上主线的原因，面试可以大方说："我读过它的 PlanningFlow，理解 Plan-and-Execute 模式，但官方标注 unstable，生产化我会选 LangGraph 或自实现，我的项目重点是工具层和 RAG。"

## 8. 汇总：四种停止条件（考核题 1 的满分答案）

1. **模型调 Terminate 工具**（主动收工，toolcall.py:218-227）；
2. **max_steps 步数耗尽**（强制兜底，base.py:149-152）；
3. **Token 超限**（上下文耗尽，toolcall.py:60-73）；
4. 循环条件本身：`state != FINISHED` 且 `current_step < max_steps`（base.py:136-137）。
