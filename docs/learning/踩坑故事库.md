## 坑 #001：OpenManus 启动期 Daytona 段缺失

**日期**：2026-09-13（W1 Day 1）
**类型**：开源底座配置 bug（模板与代码不同步）
**难度**：⭐⭐（读 Traceback + 配置层绕过，无源码改动）
**自己做的占比**：高（亲手跑命令、亲手加配置段、亲手按运行；AI 辅助读源码定位根因）

### S - Situation（情境）
首跑 OpenManus，执行 `python main.py` 后立即报错，连输入提示都没出现：

```
Traceback (most recent call last):
  File "D:\projects\OpenManus\main.py", line 4, in <module>
    from app.agent.manus import Manus
  ...
  File "D:\projects\OpenManus\app\config.py", line 297, in _load_initial_config
    daytona_settings = DaytonaSettings()
  ...
pydantic_core._pydantic_core.ValidationError: 1 validation error for DaytonaSettings
daytona_api_key
  Field required [type=missing, input_value={}, input_type=dict]
```

### T - Task（任务）
让 OpenManus 跑起来进入提问环节，完成 W1 首跑验收。

### A - Action（行动）
1. **读 Traceback 从最后一行往上**（学到的报错阅读法）：
   - 末行 = 病名：`daytona_api_key` 缺失
   - 中行 = 事发地：`app/config.py:297` 调用 `DaytonaSettings()`
   - 首行 = 起点：`main.py:4` 一启动就加载配置
2. 读源码 `app/config.py` 第 108-109 行：`DaytonaSettings` 配置类把 `daytona_api_key` 标为必填（`Field required`，无默认值）
3. 读源码第 293-297 行：启动时 `_load_initial_config` **无条件**实例化 `DaytonaSettings`——也就是说任何人按普通模板配完都会崩
4. 对比两个模板：`config.example.toml`（普通版，**无 `[daytona]` 段**）vs `config.example-daytona.toml`（Daytona 专用版，有该段）——确认模板与代码不同步，是底座 bug
5. **决策**：用配置层补字段绕过，不动源码
   - 理由 1：保持底座代码原状，将来 OpenManus 上游更新合并不冲突
   - 理由 2：面试讲"基于官方代码做二开"才干净
6. 亲手在 `config/config.toml` 文末加：
   ```toml
   [daytona]
   daytona_api_key = ""
   ```
7. 重新跑 `python main.py`，启动成功，进入 `Enter your prompt:` 提示

### R - Result（结果）
- 1 分钟修复，程序进入提问环节
- 后续首跑斐波那契成功，W1 验收核心达成
- 截图存档：`D:\projects\OpenManus\learning-notes\W1-首跑-斐波那契.png`

### 可被追问的点（自己先想好答案）
- **Q：为什么不直接改源码把 `Field required` 去掉？**
  A：改源码破坏底座，将来 OpenManus 上游更新我合并会冲突；而且面试讲"我基于官方代码做二开"才干净。配置层绕过是工程上更稳的选择。

- **Q：Daytona 是什么？为什么空 key 能过？**
  A：Daytona 是付费的云端沙箱服务，本地学习不用它；空字符串只是哄过 pydantic 的必填校验，`[sandbox]` 段没配置，代码默认不启用沙箱，工具都在本机执行，不受影响。

- **Q：Traceback 为什么从下往上读？**
  A：Python 报错最末行是病名（什么错），中间是调用栈（谁要的），首行是起点（从哪儿开始）——从病名往起点读，能最快定位根因。

- **Q：你怎么知道这是底座 bug 不是你配错了？**
  A：我对比了两个官方模板——普通版 `config.example.toml` 没有 `[daytona]` 段，只有 Daytona 专用版 `config.example-daytona.toml` 才有。但代码是无条件加载的，所以任何人按普通模板配完都会崩，这不是用户配置错误。

- ✅ `SandboxSettings`（config.py:94-104）全字段有默认值且 `use_sandbox=False`——"空 key 哄过校验、沙箱不启用、工具本机执行"的追问答案成立；

## ZCode 工程坑记录（2026-09-25 · 待学生亲手复现才升格为学生条目）

> 守则红线：故事库只收"学生亲手做"的条目。以下三坑由 ZCode 在 W2 环境交付中踩到并修复，**先记在此备考**；学生在 W2 实操中亲手复现任一坑（自己报错→自己定位→自己修），即升格为正式 STAR 条目，ZCode 记录降为脚注。

### 坑#Z01 pymysql 的 `%` 占位符吞掉 DATE_FORMAT
- **现象**：SQL 里写 `DATE_FORMAT(d, '%Y-%m')`，经 SQLAlchemy exec_driver_sql 执行报 `ValueError: unsupported format character 'Y'`。
- **根因**：pymysql 是 pyformat 参数风格，cursor.execute 会对 SQL 字符串做 `%` 格式化，裸 `%Y` 被当占位符。
- **修复**：字面百分号写双份 `%%Y-%%m`（或改用参数绑定/text 方案并实测）。
- **复现路径**：在 one_click_init.py 验证查询里写单 `%` 跑一次。

### 坑#Z02 外键清空顺序：父先子后必死
- **现象**：幂等重跑导入脚本，`DELETE FROM Customers` 报 1451 外键约束失败。
- **根因**：Transactions 引用 Customers；有子行时父表删不掉。首跑不炸只因当时表是空的——"幂等"承诺在第二次运行才暴露为假。
- **修复**：清空按子→父（Transactions→Customers→Products），导入按父→子。
- **教训句**：幂等性必须在"有数据的状态"下验证，空库跑通不算数。

### 坑#Z03 Windows bat 用 UTF-8 中文注释被 GBK 解析炸掉
- **现象**：含中文注释的 .bat 运行时报一串乱码命令"不是内部或外部命令"。
- **根因**：cmd 默认按 GBK 读批处理文件，UTF-8 中文字节被拆成乱码指令；chcp 65001 只管输出不管解析。
- **修复**：批处理内容纯 ASCII（中文放 README），或存成 ANSI/GBK 编码。
- **复现路径**：把 sync_to_openmanus.bat 第一版注释改回中文跑一次。

## 坑#002 环境变量的"默认值"把真密码漏了进去（学生条目 · 2026-09-28 · 工具1带写现场）

- **S**：写工具 1 填空 2（数据库连接），要从环境变量读密码。
- **T**：让代码"没设环境变量也能跑"，图省事。
- **A**：写成 `os.environ.get("MYSQL_PASSWORD", "root")`——默认值填了真密码。考核官带写时当场指出：这是**换位置硬编码**，密码照样进 git 历史。改为默认空串 `""`，没设环境变量就让它报错——报错比泄漏好。
- **R**：30 秒修正；测试仍全绿。
- **面试话术**："我第一版给环境变量写了含真密码的默认值，带写时被指出等于变相硬编码——默认值也会进 git 历史。改成空默认+显式报错后我记住一条：**秘密的配置项宁可启动失败，不可静默兜底**。"
- **追问预案**：Q 为什么空默认比填个假密码好？A 假密码会让"忘设环境变量"变成"连不上数据库"的迷之报错，空值+明确报错信息一眼定位。

## 坑#003 setx 设的永久环境变量，当前终端读不到（学生条目 · 2026-09-28）

- **S**：按预习包用环境变量传 MySQL 密码，`setx MYSQL_PASSWORD ...` 设完立刻跑测试。
- **T**：测试报 `using password: NO`——像密码没设。
- **A**：定位：setx 写的是注册表里的永久变量，**已打开的终端进程不会刷新环境块**；新开终端才继承。当场解法：PowerShell `$env:MYSQL_PASSWORD = "..."` 临时设，立即生效。
- **R**：临时设置后测试 PASS 2/0/6；预习包"跑测前四查"第 4 条由此诞生。
- **面试话术**："排环境变量问题时我先区分'变量没设'还是'设了但进程没继承'——setx 只影响新进程，这个差别让我少绕了半小时。"
- **追问预案**：Q 那 CI/流水线里怎么设？A 流水线每步都是新进程，setx/secret 注入天然生效；坑只出现在"人交互的长寿命终端"。

## 坑#004 PowerShell 执行策略拦住了 venv 激活脚本（学生条目 · 2026-09-30 · 工具2带写现场）

- **S**：按惯例 `.venv\Scripts\activate` 激活虚拟环境再跑测试。
- **T**：PowerShell 报"无法加载文件 activate.ps1，因为在此系统上禁止运行脚本"（PSSecurityException / UnauthorizedAccess）。
- **A**：定位：Windows PowerShell 默认执行策略禁止运行任何 .ps1，activate 本身就是 .ps1。绕过：**不激活，直接用 venv 里 python.exe 的完整路径**跑——`D:\projects\OpenManus\.venv\Scripts\python.exe <脚本全路径>`，效果等价还少一步；或换 PyCharm 内置终端（它已处理激活）。
- **R**：当场跑通；此方案已成为项目标准跑法，写进全部预习包"跑测前五查"。
- **面试话术**："Windows 环境激活脚本被执行策略拦时，我没有去改系统安全配置（最小权限原则），而是换等效路径调用解释器——排障先想'目标是什么'而不是'网上教程那一步'。"
- **追问预案**：Q 为什么不 Set-ExecutionPolicy 放开？A 那是全机安全面；学习项目不改系统策略，等效方案零风险。Q 还有哪些等价跑法？A PyCharm 终端 / cmd 下 activate.bat（批处理不受 PS 策略管）/ IDE 直接指定解释器。

## 坑#005 plotly 装错了地方：系统 Python 有、venv 里没有（学生条目 · 2026-10-02 · 工具3现场）

- **S**：工具 3 带写前环境预检：venv 里 `import plotly` 报 ModuleNotFoundError，但系统 python（6.9）明明装过 plotly。
- **T**：让测试用的解释器能用上 plotly。
- **A**：定位：**系统 python 和 venv 是两套互不相通的包目录**——pip 装到哪个，取决于当时激活的是谁；我的测试基线跑在 venv，所以必须装进 venv。解法：`uv pip install plotly --python D:\projects\OpenManus\.venv\Scripts\python.exe`（或激活后装），venv 得到 7.1。
- **R**：工具 3 顺利跑通，PASS 6/0/SKIP 2；至此"装包先问装进哪个解释器"成为肌肉记忆（同坑还有更早的 openpyxl/pymysql）。
